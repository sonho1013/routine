> **版本:** v1.0 | **日期:** 2026-04-04  
> **目标读者:** 具备技术背景的产品/项目管理层

---

## 一、问题定义：习惯学习的核心挑战

在为车载座舱设计"习惯记忆"系统之前，我们首先需要理解这个任务面临的核心挑战。以下 5 个挑战直接决定了架构中每个模块的存在理由。

| # | 挑战 | 通俗描述 | 对应模块 |
|---|------|---------|---------|
| C1 | 动作表达的开放性 | "设空调22度"和"设空调23度"是同一类习惯吗？"设空调"和"开座椅加热"差多远？系统需要理解动作语义的远近关系，而非简单的字符串匹配 | ② Signal→Fact + ③ Embedding |
| C2 | 场景的隐式性 | 用户不会说"我要创建一个早晨通勤场景"。系统必须从时间、地点、车辆状态等上下文中自动识别场景，而非预先硬编码 | ② StructuredContext + ④ Hybrid DBSCAN |
| C3 | 习惯的统计性 | 做一次不是习惯，做三次也可能只是巧合。系统需要既有统计学上的聚类证据，又有时间维度上的"连续性"验证 | ④ DBSCAN + 连续性验证 + 聚类置信度 |
| C4 | 习惯数量的未知性 | 一个用户有多少习惯？3个还是30个？系统不能预设习惯数量，必须自动发现 | ④ DBSCAN（无需预设 k） |
| C5 | 输出的可解释性 | 检测出的习惯需要人能看懂（"每天早晨通勤时设空调22度"），而非一堆数字向量 | ⑤ LLM合成 + 场景卡命名 |

## 三、逐模块合理性论证

### 模块 ① 信号输入

**做什么：** 采集座舱系统的原始车辆信号（空调温度、座椅加热、导航目的地、车窗位置、驾驶模式等）。

**为什么需要：** 这是系统的数据源。所有下游处理都基于真实的用户操作信号，而非人工标注。

**设计决策：**
- 信号格式对齐车载埋点系统标准（timestamp + signal_name + value），确保未来可直接接入真实数据源
- 不在此阶段做任何语义处理，保持原始信号的完整性

---

### 模块 ② Signal → Fact 转换

**做什么：** 将原始信号转换为两个独立组件：
- **裸动作 Fact**（自然语言文本）：`"set cabin air conditioning temperature to 22 degrees"`
- **StructuredContext**（多维上下文描述符）：时段、车辆状态、地理围栏、工作日、小时

**为什么需要（对应挑战 C1 + C2）：**

*如果没有这个模块：* 原始信号是 `{signal: "hvac_temp_target", value: 22}` 这样的键值对，无法进行语义理解。"设空调22度"和"设空调23度"在键值对世界里是完全不同的两条记录，无法被识别为"同一类习惯"。

**关键设计决策 — 文本与上下文分离：**

这是整个架构最重要的设计决策之一。我们刻意将"用户做了什么"（文本）和"在什么场景下做的"（上下文）分开存储，而非将场景信息编码到文本中。

| 方案 | 示例 | 问题 |
|------|------|------|
| 场景编码到文本 | "morning commute: set AC to 22°C" | 文本 embedding 中混入场景语义，导致"早晨设空调22度"和"晚上设空调22度"在向量空间中被拉远，模型难以理解"设空调"这个动作本身的相似性 |
| **文本与上下文分离**（当前方案） | text: "set AC to 22°C" + ctx: {time: early_morning} | 文本 embedding 专注于捕捉动作语义，上下文通过独立的距离函数处理。两者按权重组合，各司其职 |

**技术合理性：** 分离设计使得同一动作在不同场景中的文本 embedding 完全相同（距离=0），区分完全由 StructuredContext 距离贡献。这让混合距离的权重（α=0.8 文本 + 0.2 上下文）含义清晰，可调可解释。

---

### 模块 ③ ChromaDB 存储

**做什么：** 
- 使用 OpenAI ada-002 将 Fact 文本编码为 1536 维向量
- 向量 + 结构化上下文元数据持久化存储在 ChromaDB

**为什么需要（对应挑战 C1）：**

*如果没有向量化：* 只能做字符串精确匹配或关键词匹配。`"set AC to 22°C"` 和 `"set AC to 23°C"` 在字符串世界里完全不同，但在向量空间中距离仅 0.017（相似度 98.3%），能被正确识别为"同一类动作"。

**为什么选 ChromaDB：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **ChromaDB**（当前） | 本地部署、零运维、支持元数据过滤、Python 原生、持久化存储 | 不适合超大规模（>100万条） |
| Pinecone/Weaviate | 云端托管、自动扩缩 | 增加外部依赖、网络延迟、成本 |
| 纯 numpy 矩阵 | 最简单 | 无持久化、无元数据过滤、需要自建索引 |

对于车载场景（单用户数百~数千条 facts），ChromaDB 的本地化和轻量级特性是最合适的选择。

**为什么选 ada-002：**
- OpenAI 最成熟的通用文本 embedding 模型，1536 维
- 已通过实际验证：同类动作组内最大距离 0.065，跨场景最小距离 0.133，分离度足够（详见第四章）
- 后续可无缝替换为其他 embedding 模型（如本地部署的模型），接口兼容

---

### 模块 ④ Hybrid DBSCAN 聚类

**做什么：** 使用混合距离度量（文本语义 + 结构化上下文）自动发现习惯聚类。

**这是整个系统的核心创新。** 包含四个子组件：

#### 4a. 混合距离矩阵

```
混合距离 = 0.8 × 文本余弦距离 + 0.2 × 上下文距离
```

**为什么需要混合距离（对应挑战 C2）：**

| 方案 | 效果 |
|------|------|
| 仅文本距离 | "早晨设空调22度"和"晚上设空调22度"距离=0，无法区分不同场景下的相同动作 |
| 仅上下文距离 | 同一场景下的不同动作（如"设空调"和"开座椅加热"）距离=0，全部混在一起 |
| **混合距离**（当前） | 文本负责区分动作类型，上下文负责区分场景。α=0.8 表示以动作语义为主、场景为辅 |

**α=0.8 的依据：** 实验验证表明，动作类型的区分主要靠文本语义（不同动作的文本距离差异远大于上下文距离差异）。0.2 的上下文权重足以将同一动作在不同场景中分开，同时不会因为上下文噪声（如同一天早8点 vs 早7点）误拆真正的习惯。

#### 4b. DBSCAN 聚类

**为什么选 DBSCAN 而非 K-Means（对应挑战 C4）：**

| 特性 | K-Means | DBSCAN |
|------|---------|--------|
| 需要预设聚类数 k | 是 — 用户有多少习惯？无法预知 | **否** — 自动发现 |
| 处理噪声 | 所有点必须归入某个聚类 | **自动识别噪声点**（一次性、偶发行为） |
| 聚类形状 | 仅球形 | **任意形状** |
| 适合性 | 不适合 — 习惯数量未知、存在噪声 | **适合** — 自动发现聚类 + 过滤噪声 |

**参数选择：**
- `ε=0.10`：经 embedding 距离验证报告确定，在此阈值下聚类纯度 >93%
- `min_samples=3`：每个信号类型每天产生 1 条 Fact，5 天数据中部分信号不是每天都有（如座椅加热只在冷天开），3 比 5 更稳健

#### 4c. 连续性验证

**为什么需要（对应挑战 C3）：**

DBSCAN 只看语义相似度，不看时间顺序。但"习惯"要求的是**最近连续**的行为模式。

场景示例：
```
Day1: 设空调 22°C  ──┐
Day2: 设空调 22°C  ──┼── DBSCAN 聚出这 4 条
Day3: 设空调 24°C  ──┤   但 Day3 不在聚类中
Day4: 设空调 22°C  ──┤   → 最近 5 次中只有 4 次在聚类
Day5: 设空调 22°C  ──┘   → 连续性验证不通过 → 不提升为习惯
```

*如果没有连续性验证：* 用户一个月前的旧习惯（已经改变）也会被错误提升为当前习惯。

**算法：**
1. 提取聚类的主导信号名 + 主导上下文
2. 在全量 facts 中找同信号 + 相似上下文的候选集
3. 按时间排序，取最近 N 条（默认 5）
4. 检查最近 N 条是否全部在聚类中

#### 4d. 聚类置信度

**为什么需要（对应挑战 C3）：**

不是所有聚类都同样可靠。系统为每个聚类计算一个 0~1 的质量分数：

| 维度 | 权重 | 含义 |
|------|------|------|
| 紧凑度 cohesion | 50% | 成员间距离有多近。距离越小 = 行为越一致 |
| 核心点占比 core_ratio | 25% | 聚类中有多少"核心成员"。全是核心点 = 聚类稳定 |
| 证据充分度 size_factor | 25% | 聚类有多少条数据支撑。数据越多 = 证据越充分 |

**作用：**
- 提供不依赖 LLM 的客观聚类质量信号
- 低置信度的聚类可以被标记为"待观察"而非直接推荐
- 与 LLM 合成置信度、场景命名置信度形成多维可信度体系

### 模块 ⑤ 习惯输出

**做什么：** 将聚类结果转化为人可理解的习惯描述和场景名。

包含两个子组件：

#### 5a. LLM 习惯合成（GPT-4.1）

**为什么需要（对应挑战 C5）：**

聚类结果是一组相似 fact 文本：
```
- "set cabin air conditioning temperature to 22 degrees"
- "set cabin air conditioning temperature to 23 degrees"  
- "set cabin air conditioning temperature to 22 degrees"
- "set cabin air conditioning temperature to 22 degrees"
- "set cabin air conditioning temperature to 23 degrees"
```

*如果没有 LLM 合成：* 只能取第一条文本或做简单拼接，无法生成自然流畅的习惯描述。

*LLM 合成后：* `"通常将空调温度设定在 22-23 度之间"` — 自然、准确、包含值域范围。

#### 5b. 场景卡命名

**为什么需要（对应挑战 C2 + C5）：**

回顾核心设计：全流程无预定义场景标签。场景名在此阶段**首次出现**，由 LLM 根据上下文自动生成。

流程：
1. 将上下文相似的习惯分组（如同为 early_morning + engine_started 的习惯）
2. LLM 根据组内习惯和上下文生成场景名（如 "Morning Commute"，置信度 0.96）
3. 场景名写入每个 habit 的元数据

**与硬编码场景的对比：**

| 方案 | 可扩展性 | 准确性 |
|------|---------|--------|
| 硬编码场景（"通勤"/"回家"/"停车"） | 差 — 新场景需要改代码 | 可能误分 — 规则无法覆盖所有组合 |
| **LLM 动态命名**（当前） | 好 — 新场景自动被 LLM 命名 | 高 — LLM 综合上下文和习惯内容推理 |

## 四、Text Fact 有效性论证

### 核心问题

> "用纯文本描述用户动作，然后通过 embedding 向量化 → 能否可靠地区分不同动作、识别相同动作？"

### 验证结论

**答案是肯定的。** 系统使用的混合距离（0.8×文本+0.2×上下文）在所有测试场景中均能正确区分。

### 相似度配对表（基于实际数据）

以下基于 83 条 facts（5天模拟数据）的真实 embedding 计算。相似度 = `(1 - 混合距离) × 100%`。

**应该聚在一起的（同动作 + 同场景）：**

| 文本 A | 文本 B | 混合相似度 | 判定 |
|--------|--------|-----------|------|
| set AC temperature to 22 degrees | set AC temperature to 23 degrees | 96.1% | PASS — 正确识别为同类 |
| turned on seat heating to level 2 | turned on seat heating to level 2 | 97.5% | PASS — 完全相同文本+相同上下文 |
| started navigation to work | started navigation to work | 97.5% | PASS — 完全相同文本+相同上下文 |
| resumed listening to podcast Tech Daily | resumed listening to podcast Morning Brew | 95.5% | PASS — 不同播客名但同类动作 |

**应该分开的（不同动作 / 不同场景）：**

| 文本 A | 文本 B | 场景差异 | 混合相似度 | 判定 |
|--------|--------|---------|-----------|------|
| set AC to 22°C (早晨通勤) | turned off AC (到家) | 动作不同 + 场景不同 | 74.7% | PASS — 正确分开 |
| set AC to 22°C (早晨通勤) | started navigation to work (早晨通勤) | 动作不同 + 场景相同 | 83.1% | PASS — 文本距离拉开 |
| set AC to 22°C (早晨通勤) | lowered window 50% (收费站) | 动作不同 + 场景不同 | 72.1% | PASS — 正确分开 |
| switched to eco mode (随机噪声) | switched to eco mode (早晨通勤) | 动作相同 + 场景不同 | 81.7% | PASS — 上下文距离拉开 |

**关键分离线：** DBSCAN ε=0.10 → 相似度阈值 = 90%。**高于 90% 聚在一起，低于 90% 分开。** 上表中：同类全部 ≥95.5%，异类全部 ≤83.1%，中间有 12+ 个百分点的安全间隔。

> 可视化版本见附录 A1 `output/fig4_similarity_pairs.png`

### 为什么纯文本 + 上下文比结构化字段更好

| 方案 | "设空调22度" vs "设空调23度" | 新增信号类型 | 语义理解 |
|------|---------------------------|------------|---------|
| 结构化字段 (signal + value) | 完全不同的记录，需要写规则定义"差 1 度算同类" | 需要改代码新增字段 | 无 |
| **文本 + Embedding**（当前） | 自动识别为 98% 相似 | 只需新增文本模板 | Embedding 自带语义理解 |

## 五、替代方案对比

| 维度 | 纯规则引擎 | 纯 LLM 方案 | 传统统计（频次计数） | **当前方案（Hybrid DBSCAN）** |
|------|-----------|------------|-------------------|---------------------------|
| 习惯发现 | 手写规则，覆盖有限 | LLM 直接判断，成本高、不稳定 | 需预定义动作类别 | 自动发现，无需预设数量 |
| 场景识别 | 硬编码场景列表 | LLM 可推理但无结构化保证 | 需预定义场景 | 上下文自动聚类 + LLM 命名 |
| 噪声处理 | 需手写过滤规则 | LLM 判断不稳定 | 低频即噪声，过于简单 | DBSCAN 天然过滤噪声 |
| 可解释性 | 规则透明 | LLM 黑箱 | 频次统计透明 | 聚类置信度 + LLM 合成双重可解释 |
| 新增信号 | 改规则代码 | 改 prompt | 改类别定义 | 仅需新增文本模板 |
| 计算成本 | 低 | 高（每条信号调 LLM） | 低 | 中（embedding 一次 + 矩阵运算） |
| **综合** | 维护成本高，覆盖有限 | 成本高，结果不稳定 | 表达能力不足 | **平衡准确性、可扩展性和成本** |

## 六、验证结果摘要

| 指标 | 数值 | 说明 |
|------|------|------|

| 聚类纯度 | 100%（eps≤0.08） | 零跨场景污染 |
